## 一、结论（先给结论）

1. 该工程是典型 2018 年代 Spring Cloud Netflix 全家桶示例级微服务（SpringBoot 2.0.3.RELEASE + Spring Cloud Finchley + JDK 1.8），其依赖栈（Zuul / Eureka / Hystrix / Turbine / spring-cloud-oauth2 / Sleuth）**全部已 EOL 或从 Spring Cloud 2020+ 中移除**，升级到 SpringBoot 3.x 属于"组件整体替换"而非"版本号升级"，无法渐进兼容。
2. 账务相关核心链路（account-service 的 create / saveChanges，statistics-service 的汇率换算与统计落库）存在**无事务边界、跨服务无补偿、先写用户后写账户的分布式一致性缺陷、金额精度处理不严谨**等问题，属于金融红线区域，本次升级**只允许做等价迁移，禁止顺手改业务逻辑**；所有涉及该链路的变更单独标记为高风险，须人工审核。
3. 推荐目标版本组合（与 Nacos 3.0.3 官方对齐）：
   - JDK 17
   - Spring Boot 3.5.x
   - Spring Cloud 2025.0.x
   - Spring Cloud Alibaba 2025.0.0.0（其内置 nacos-client 即为 3.0.3，与用户指定的 Nacos 3.0.3 服务端匹配）
   - 注册中心 + 配置中心：Nacos 3.0.3（替换 Eureka + Spring Cloud Config）

### 2.3 数据库访问层现状

- 全部使用 Spring Data MongoDB（CrudRepository），每个服务独立 mongodb 实例（按库隔离，符合微服务数据私有原则）。
- 无任何 JPA/MyBatis；无关系型数据库；无数据库级事务。
- MongoDB 单文档写为原子操作，但工程中**没有任何显式事务（无 @Transactional，MongoTransactionManager 未配置）**，多文档/跨服务写全靠代码顺序保证。
- 账户主键直接用业务字段 name 作为 @Id（account-service Account.name、notification Recipient.accountName），statistics 用复合主键 DataPointId(account, date)。

### 2.4 事务边界与接口依赖（关键调用链）

1. 开户链路（POST /accounts/）：
   AccountServiceImpl.create() →
   a) repository.findByName 查重（非原子，存在竞态）→
   b) authClient.createUser(user)（远程 HTTP 写 auth 库）→
   c) repository.save(account)（本地写 account 库）
   **风险：b 成功、c 失败 → 产生孤儿用户；无补偿、无幂等键、无事务。**
2. 账务变更链路（PUT /accounts/current）：
   saveChanges() → 本地 save 后同步 Feign 调 statisticsClient.updateStatistics()
   - 有 Hystrix fallback，但 fallback 仅打日志 → **统计静默丢失，账务与统计最终不一致，无对账机制。**
3. 统计链路：StatisticsServiceImpl.save() 内多次调 ratesService.convert()，
   ExchangeRatesServiceImpl 用**普通成员变量 container 做当日汇率缓存，无锁**（并发/数据一致性风险，见 3.2）。
4. 通知链路：@Scheduled 定时任务 + CompletableFuture.runAsync(公共 ForkJoinPool) 逐个发信后 markNotified，
   **多实例部署会重复发送；发送成功但 markNotified 失败会再次重发；无幂等控制。**

### 2.6 潜在并发 / 数据一致性风险清单

| # | 风险 | 级别 | 说明 |
|---|---|---|---|
| R1 | 开户"查重+插入"非原子（findByName→save 竞态） | 高 | 并发注册同名账户可产生重复写；MongoDB _id 冲突会抛异常但 auth 侧用户已创建，无法回滚 |
| R2 | create() 先远程写 auth 再本地写 account，无分布式事务/补偿/幂等 | 高（账务红线） | 中途失败产生孤儿数据，不可追溯 |
| R3 | saveChanges() 账务保存与统计更新非事务，fallback 吞错 | 高（账务红线） | 统计与账务永久不一致，无对账/重试队列 |
| R4 | ExchangeRatesServiceImpl.container 无同步的懒加载共享状态 | 中 | 并发下重复拉取外部 API、可能读到半初始化对象；日期切换瞬间多请求同时刷新 |
| R5 | 汇率 convert() 除法保留4位 HALF_UP 后 multiply，多次换算精度累积误差 | 中（金额红线） | 金融金额应统一 scale/RoundingMode 策略并全链路一致；本次迁移不改算法，仅标记 |
| R6 | 定时通知任务无分布式锁、无幂等 | 中 | 多实例重复发邮件；markNotified 失败重发 |
| R7 | CompletableFuture.runAsync 使用公共 ForkJoinPool，无背压 | 中 | 大量收件人时线程饥饿、异常被吞 |
| R8 | 账户读接口 getAccountByName 仅靠 @PreAuthorize SpEL，"/{name}"可被 server scope 客户端任意读取 | 中 | 升级时需按新 Security 模型等价复核，不得放宽 |
| R9 | DataPoint 按天 upsert，同一天多次 saveChanges 直接覆盖 | 低 | 现状业务如此，迁移时保持等价语义，不擅自改为追加 |
| R10 | InMemoryTokenStore 重启丢会话 | 中 | 升级方案中一并解决（JDBC/Redis token 或 JWT 无状态） |
