## 3. 部署顺序与编排（强依赖，实测固化）

```
1. mysql（Nacos 外置存储，生产必须；开发可 standalone 内嵌 derby）
2. nacos（healthcheck 通过后才继续 —— 见 3.2 健康检查修正）
3. 【关键新增步骤】Nacos provision：建 namespace + 发布配置 + 读回校验（见第 4 节）
4. sentinel-dashboard（可选）
5. auth-service          ← 业务服务最先（JWT issuer/JWKS 提供方）
6. account/statistics/notification-service（并行）
7. gateway               ← 最后（lb:// 路由依赖 Nacos 已有实例）
```

docker compose 已用 depends_on(nacos: service_healthy) 固化 5-7 步；**第 3 步 provision 无法由 compose 表达，必须在 nacos healthy 后、业务服务启动前人工/脚本执行**（否则 optional:nacos: 前缀会让服务以本地兜底配置静默启动，配置中心形同虚设——两轮联调实证此顺序）。

一键序列（实测，两轮全链路联调即用此序列）：
```
mvn clean package -DskipTests
docker compose build
docker compose up -d mysql nacos sentinel-dashboard
# 等 nacos healthy：docker inspect --format '{{.State.Health.Status}}' nacos-3.0.3
python3 provision-main-nacos.py          # 建 dev 命名空间 + 发布 6 配置 + 读回校验
docker compose up -d                     # 全部服务（depends_on 门禁自动排序）
python3 verify-main-compose.py           # 31 项全链路断言，期望 PASS=31 FAIL=0
```

### 3.1 网络拓扑（🔴 B7 教训，必须遵守）

**nacos 必须与业务服务同网络**。主 compose 曾把 nacos/mysql 放独立 nacos-net、业务服务在 default，导致服务解析不到 host `nacos`（config 8848 与 discovery gRPC 9848 全部 UnknownHostException），5 服务启动即崩溃 exit 1。修复（已入主 compose）：

```yaml
  nacos:
    networks:
      - nacos-net     # 与 mysql 互通
      - default       # 与业务服务互通（B7 修复，不可删）
```

自检：服务日志出现 `Load config[dataId=...] success` 与 `nacos registry ... register finished` 即网络正确；出现 `Client not connected, current status:STARTING` 即网络拆分复发。

### 3.2 Nacos 容器编排要点（实测修正三处）

```yaml
  nacos:
    image: nacos/nacos-server:v3.0.3
    environment:
      MODE: standalone                       # 生产改集群 + 外置 MySQL（本机联调即 mysql:8.0.46）
      NACOS_AUTH_TOKEN: ${NACOS_AUTH_TOKEN}  # ⚠️ 3.x 强制要求（Base64，解码≥32字节），即使 AUTH_ENABLE=false；缺失容器启动即退出
      NACOS_AUTH_IDENTITY_KEY: serverIdentityKey
      NACOS_AUTH_IDENTITY_VALUE: serverIdentityValue
    healthcheck:
      # ⚠️ /nacos/actuator/health 在 3.x 返回 404（旧文档写法错误），必须探测 v3 admin state：
      test: ["CMD", "curl", "-sf", "-H", "serverIdentityKey: serverIdentityValue",
             "-o", "/dev/null", "http://localhost:8848/nacos/v3/admin/core/state"]
      interval: 10s
      timeout: 5s
      retries: 30
      start_period: 30s
```

|---|---|---|

### 4.2 自动化脚本（工程根，均已实测）

```
python3 provision-main-nacos.py    # 幂等：建 namespace(dev) + 发布 6 配置 + 读回字节比对 + 掩码完整性检查
```

脚本行为与实测注意事项：
- 登录：POST /nacos/v1/auth/login → accessToken；**auth 关闭的部署该接口返回 500（"Handle API Compatibility failed"），脚本已容忍，改用匿名 + identity header**（serverIdentityKey/serverIdentityValue）。
- namespace：v1 console API 在 3.x 已移除（410）；**必须用 v3 admin**：POST /nacos/v3/admin/core/namespace（form: namespaceId/namespaceName/namespaceDesc + identity header）。
- 配置发布：v1 POST /nacos/v1/cs/configs（tenant=<namespace>）仍可用；**发布返回 true 后首次读回可能不一致（写后读时序），sleep 3s 重跑即一致**——脚本内置重试与完整性检查（拒绝含 U+2026/*** 的损坏内容，B5 教训）。
- 🔴 B5 教训：配置模板中的占位符 `${MONGODB_PASSWORD:}` 曾被工具链掩码损坏为 `${MONGODB_PASSWORD:***` 并成功发布，导致 4 服务 Mongo 认证失败（SCRAM AuthenticationFailed）。**任何配置发布必须过读回比对 + 完整性检查，禁止"发布成功即认为内容正确"。**

### 4.3 生产环境差异项

- issuer-uri/token-uri 默认值是容器网络名（http://auth-service:5000/uaa）；跨网段/域名部署时在对应 namespace 的 <service>.yml 覆盖为实际地址。
- rates.url 替换为生产牌价服务（P2）。
- staging/prod：同脚本 `--namespace <env>` 式发布（provision 脚本改 NAMESPACE 常量或参数化）；namespace 隔离即回滚隔离。
- 配置热生效：@RefreshScope Bean（EmailServiceImpl）即时；**Feign url（rates.url）、JWT issuer、路由类配置需重启对应服务生效**（Feign client url 在启动时绑定，联调实证）。

## 6. 运维要点

| 场景 | 操作 |
|---|---|
| 扩缩容 | 业务服务无状态（JWT 本地校验）可直接水平扩展；**前提 P1 完成（固定签名密钥）**；notification 多实例由 ShedLock(Mongo) 保证定时任务单次执行 |
| 滚动发布 | 先下游后网关；auth-service 多实例期间必须已完成 P1 |

| 服务异常自检 | 日志三大信号：`Load config ... success`（配置）→ `nacos registry ... register finished`（注册）→ `Started <Svc>Application`（启动）；缺哪步查哪层（配置失败查 4 节，注册失败查 3.1 网络） |
| 日志 | pattern 含 [服务名,traceId,spanId]，按 traceId 检索全链路 |
| 监控 | actuator health/info/metrics（gateway 另暴露 gateway 端点）；Sentinel Dashboard :8858 |
| 告警建议 | 健康检查失败；Sentinel 降级触发；Feign fallback ERROR 关键字 "Error during update statistics"（H4 静默降级现状，立项前靠告警兜底）；Nacos 连接失败 |

## 7. 已知部署限制与决策记录（如实声明）

1. 【🔴 生产阻塞】H6：JWT 密钥启动时生成 + InMemoryOAuth2AuthorizationService（refresh 簿记内存态）。单实例可用（联调实证），多实例/生产必须先接 KMS 固定密钥 + 共享授权存储。
2. 【🔴 生产阻塞】D16：汇率源已停服。rates-mock 仅联调组件，生产编排不含它；无可用源时统计链路走 fallback（空 rates 将 NPE，K2 已锁定为已知现状）。
3. 【已决策 2026-10-01】配置拉取策略：保留 `optional:nacos:` + 本地完整默认值（Nacos 不可达时降级本地启动，回滚设计）；不做 fail-fast。**副作用须知：Nacos 配置缺失时服务不会报错而是静默用本地值——所以第 3 节把 provision 列为强制步骤，验证第 2 类断言（Load config success）不可跳过。**
4. Nacos standalone 仅开发；生产 3 节点集群 + 外置 MySQL（联调已用 mysql:8.0.46 外置存储验证该形态，schema 由 Nacos 首启自动初始化，约 30s 内 healthy）。
5. Sentinel Dashboard 为社区镜像（bladex），生产建议自建官方镜像；服务侧 SENTINEL_DASHBOARD 环境变量须与 Dashboard 实际端口对齐（compose 已注入 8858）。
6. mongodb 初始化镜像 legacy（mongo:4.4 + mongo shell + killall 逻辑），仅限开发 seeding。
7. macOS 部署需 docker-compose.override.yml（AirPlay 端口冲突）；Linux 删除之。`version: "3.8"` 属性 obsolete 警告可忽略（或删行）。
8. 冷启动可复现性已验证（2026-10-02 第 2 轮）：空状态（无容器/无命名卷）下按第 3 节一键序列执行，31/31 PASS。

## 8. 回滚（部署视角摘要，详见《回滚方案.md》）

- 配置级：Nacos 历史版本回滚（分钟级）。
- 服务级：旧版镜像 tag 保留，单服务回退；**认证体系（auth+3资源服务+gateway）必须整体同进退**（JWT/opaque 不混跑）。
- 全栈级：`docker compose down`（不带 -v 保数据）→ 旧工程目录 `docker compose up -d`（旧栈零修改保留于 /workspace_tke/piggymetrics）。
- 数据级：本次重构零 DDL/零迁移，无数据回滚需求；ShedLock 新增 shedlock 集合旧版自动忽略，无害。
