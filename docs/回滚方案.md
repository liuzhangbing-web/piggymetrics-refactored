# piggymetrics 重构回滚方案（全阶段通用）

> 原则：本次重构为"新旧并存、只增不删"——原工程 /Users/liuzhangbing/Downloads/D/workspace_tke/piggymetrics 全程零修改，回滚 = 切回旧栈，无数据迁移负担。

## 1. 回滚触发条件（任一满足即启动回滚评审）

| # | 条件 | 判定依据 |
|---|---|---|
| T1 | 🔴 红线用例失败且 24h 内无法修复 | 阶段4 测试报告（账务顺序/金额一致性/鉴权等价任一项） |
| T2 | 生产冒烟：开户或账务变更链路失败率 > 0 且无法热修 | 部署后验证清单第 6 项 + 告警 |
| T3 | 鉴权异常：出现越权（403 应拦截未拦截）| 安全用例 ACC-C03/STA-C02 类问题在生产复现——**立即回滚，最高优先级** |
| T4 | Nacos 3.0.3 与 nacos-client 3.0.3 对接出现注册/配置不可用且降级无效 | 服务注册列表缺失、配置拉取失败 |

| T6 | JWT 密钥事故（密钥泄露/多实例互验失败面扩大） | 安全事件流程 |

## 2. 回滚层级与操作（从轻到重，优先高层级）

### L0 配置级回滚（分钟级，首选）

适用：配置错误、参数不当（超时、cron、路由、Sentinel 规则）。

```
1. Nacos 控制台 -> 配置管理 -> 对应 dataId -> 历史版本 -> 回滚
2. @RefreshScope Bean 即时生效；其余配置滚动重启对应服务
3. 验证：重跑受影响的冒烟项
```

### L1 服务级回滚（10 分钟级）

适用：单个新版本服务异常（如 notification ShedLock 行为异常）。

```
1. 停止新版单服务容器
2. 以旧版镜像重启该服务（旧镜像 tag 须保留，禁止覆盖）
3. 注意混合版本约束：
   - 旧版服务用 opaque token + user-info 回调鉴权，新版用 JWT 本地校验
   - auth-service 不可新旧混跑（token 体系不同）：若回滚 auth-service，
     所有资源服务必须一并回滚（见 L2）
4. 验证：该服务 health + 相关业务冒烟
```

⚠️ 兼容性矩阵（混合部署约束）：

| auth-service | 资源服务 | 可行性 |
|---|---|---|
| 新(JWT) | 新(JWT) | ✅ 目标态 |
| 旧(opaque) | 旧(回调) | ✅ 回滚态 |
| 新 | 旧 | ❌ 旧服务回调 /uaa/users/current 仍可通（新版保留了该端点），但 scope 断言体系不同，未验证，禁止 |
| 旧 | 新 | ❌ 新资源服务器 JWT 校验对 opaque token 全部 401，禁止 |

结论：**认证体系回滚必须整体（auth + 3 资源服务 + gateway 同时回退）**。

### L2 全栈回滚（30 分钟级，标准回滚路径）

```
1. 冻结变更：停止新版发布流水线
2. 停新编排：docker compose down（新 compose，注意不带 -v，保留数据卷）
3. 起旧编排：cd /Users/liuzhangbing/Downloads/D/workspace_tke/piggymetrics && docker compose up -d
   （旧工程 registry/config/monitoring/turbine/gateway/auth/account/statistics/notification 全套）
4. 数据库：无需任何操作（本次重构零 DDL/零数据迁移；
   DataPointId Converter 字段名不变，新旧代码读同一份数据均兼容）
5. 验证（旧栈冒烟）：
   - curl http://<gw>:4000/actuator/health（旧 zuul 无此端点时用 /uaa/oauth/token 取 token 验证）
   - 旧 token 端点 POST /uaa/oauth/token 返回 access_token
   - 开户/账务变更/统计查询三条链路各跑一次
6. 事后：故障复盘 -> 修复 -> 重新走阶段3/4 验证后方可再次上线
```

### L3 数据级回滚

本次重构**不存在数据级回滚需求**（无 schema 变更、无数据迁移、无索引变更）。
若未来 H 类立项（如 H5 审计字段、H7 唯一索引）实施后需回滚，该变更单必须自带：
- mongodump 前置备份 + 恢复脚本
- 索引删除脚本（createIndex 的逆操作）
- 严禁 drop/truncate/deleteMany 无条件删除

## 3. 回滚演练要求（上线前必须完成一次）

| 演练项 | 通过标准 |
|---|---|
| L0 Nacos 配置回滚 | 改一个配置→回滚→服务行为恢复，全程 < 5 分钟 |
| L2 全栈回滚 | 新栈运行→down→旧栈 up→三条业务链路冒烟通过，全程 < 30 分钟 |
| 数据兼容双向验证 | 新代码写入的 datapoints/accounts 文档，旧代码可正常读取（抽样比对） |

## 4. 回滚责任与记录

- 回滚决策人：变更评审负责人（🔴 T3/T6 安全类可由值班安全负责人直接触发，事后补评审）
- 每次回滚必须记录：触发条件编号、时间线、影响面、数据核对结果、复盘链接
- 回滚后 24h 内输出故障报告，红线区域问题须同步风控

## 5. 不可回滚点声明（诚实披露）

| 项 | 说明 |
|---|---|
| 旧栈组件 EOL | 回滚到旧栈 = 回到无安全补丁状态，回滚只是止血，不可长期驻留 |
| token 端点变更期间发出的 JWT | 回滚后旧栈无法校验 JWT，所有会话需重新登录（用户侧感知：一次性全员掉线） |
| 新版运行期间写入的数据 | 格式与旧版兼容（已验证字段名不变），无不可回滚数据；但 ShedLock 的 shedlock 集合为新增集合，旧版忽略之，无害 |
