1. 方案A 已实施完成并通过三层验证：**单元测试 87/87 全绿（新增 12 用例）、E2E 补偿自愈 11/11 PASS、主链路回归 31/31 PASS**。
2. 阶段1实证的两个一致性缺口均已消除：

3. **红线守护**：成功路径调用顺序（findByName→createUser→save）、异常传播语义、fallback 保可用性语义（PUT 仍 200）全部由既有红线测试（ACC-03/05/06/08）+ 新增 COMP-04/06 双重锁定，无一变更。
4. 零新增基础设施：任务表存于 account-service 自己的 MongoDB（collection `compensation-tasks`），对账 Job 为服务内 @Scheduled。

## 四、风险评估

| 风险 | 等级 | 缓解 |
|---|---|---|
| 补偿删除误删正常用户 | 低 | DELETE_AUTH_USER 任务仅在"createUser 成功后本地 save 失败"的 catch 块内产生；delete 端点仅 SCOPE_server；有 WARN 审计日志可追溯 |
| 对账 Job 与在途请求并发 | 低 | 任务入队有 PENDING 查重；重算幂等（同输入同输出）；delete 幂等（不存在=false） |
| Job 高频空转开销 | 低 | 30s fixedDelay + 空列表即返回；单服务实例无并发调度问题（多实例部署时建议加分布式锁或仅单实例开启——见遗留） |
| FAILED 任务无人处理 | 中 | ERROR 级"COMPENSATION ALERT"日志已接 SkyWalking 告警体系（RT/SLA 规则同通道）；运维手册需加巡检项（见遗留） |
| statistics 客户端双份（主+补偿） | 低 | contextId 隔离，端点/语义一致仅降级策略不同，注释已说明设计原因 |

## 五、回滚方案

- **L0（配置级）**：Nacos 将 `compensation.reconcile-interval-ms` 设为极大值（如 86400000）→ Job 实质停摆，入队仍发生但不执行；
- **L1（代码级）**：revert 本次提交（新增 4 文件删除、3+3 文件还原）→ 行为回到阶段1状态（缺口重现但不恶化）；业务数据无 schema 变更，`compensation-tasks` 集合可直接废弃，无数据迁移/回滚需求；
- 兼容性：新 auth DELETE 端点为纯新增，旧版本 account-service 不调用即无感知——**支持 account/auth 两服务独立回滚、灰度混布**。

## 六、遗留事项

1. **多实例部署**：对账 Job 需分布式锁（ShedLock/Mongo 锁）或指定单实例运行，当前 compose 单实例无此问题；
2. FAILED 任务巡检纳入运维手册 + SkyWalking 告警规则可加"COMPENSATION ALERT"日志关键字告警；
3. 任务表可加 TTL 索引清理 DONE 历史记录（当前量级无需）;
4. 方案B（Seata TCC）维持"业务出现真实资金双写时再立项"的既定结论，本次未实施。
